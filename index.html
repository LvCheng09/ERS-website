A reasoning system should explain more than why an answer sounds plausible. It should identify the facts used, the operation that transformed them, the conditions that made that operation admissible, and the surviving evidence for the final claim. If an input changes, the system should be able to identify which conclusions require reconsideration.

The Event Reasoning System (ERS) explores this design through an explicit Event Graph and a library of composable Rules. A semantic frontend translates language into structured objects, attributes, relations, and evidence references. Semantic retrieval nominates candidate operations; declared Rule conditions determine which may execute. Low-level Rules transform the current state, while goal-directed Control Rules organize subgoals, candidate paths, and recovery. Each admitted operation may supply evidence for another, and final presentation requires explicit goal and support checks. The research architecture also investigates dynamically composed control hierarchies and dependency-preserving revision beyond the bounded capabilities of the public Demo.

Research and implementation. The paper presents ERS as a reasoning architecture; the linked Demo v0.1 provides a two-domain inference implementation. Research-only mechanisms and paper experiments should be read separately from released runtime behavior.

01 — The gap

A plausible answer is not a valid path

Long-horizon reasoning must solve three distinct problems. Interpretation: what entities, quantities, relations, time periods, and qualifications does the input actually express? Admission: which operations do these facts authorize under the current constraints? Organization: which admissible operation should be attempted next, when should a subgoal change, and when should a failed branch be revised?

ERS gives these questions separate responsibilities. Semantic interpretation prepares the Event state; declared Rule contracts test applicability; and Control organizes admissible operations into a task-dependent path. This makes the trace more useful for diagnosing a problem: incorrect source interpretation, an unsatisfied premise, a failed calculation, and an exhausted search budget lead to different possible responses.

CoT / ReAct / ToT

Language and tool traces

Language and tool traces expose intermediate actions, but a readable trace alone does not verify that every premise was valid or that each transition was admissible.

Program & solver hybrids

Program or symbolic form

Programs can verify operations within their formal semantics. ERS adds a task-scoped boundary from open-ended semantic input to declared evidence and Rule applicability.

World models

Learned latent states

Learned transitions can support prediction and planning. When their supports remain latent, premise-level checks and targeted revision may require additional machinery.

ERS

Explicit event graph

Event Graphs maintain task facts and scope; matched Rules perform admissible transformations; Control manages paths and feedback; output checks gate conclusions.

Positioning follows from stated design assumptions rather than measured performance (Table 1 in the paper).

02 — Architecture

Four elements, one bidirectional loop

ERS organizes reasoning around semantic access, an explicit task state, executable local Rules, and goal-directed Control. Their shared interface is an evolving Event Graph: a workspace for grounded input facts, accepted intermediate results, and the next Rule's bindings.

Semantic access

Normalizes text into spans, relations, values, and evidence references. Core, relation, and nature features propose candidate meanings without authorizing their execution.

Explicit events

Maintain identities, source scope, periods, relations, derived spans, and intermediate task states for subsequent Rule binding and inspection.

Low-level rules

Declare required input patterns and applicability conditions, then perform bounded transformations of the current Event state.

High-level control rules

Use goals, missing prerequisites, current candidates, execution feedback, and budgets to organize the next Rule or strategy.

The interaction runs in both directions. Control makes a scoped decision; Matcher checks current evidence; Executor performs an admitted operation and returns a state update or failure. That update changes which Rules can match next, while the outcome informs the next Control decision. A proposed output remains provisional until the applicable completion and output gates accept it.

What happens between a sentence and an accepted answer?

01 — Semantic frontend and graph boundary

The text entry uses Qwen/Qwen3-8B to identify events, spans, mainlines, and explicit relations. The representation is normalized, vectorized, and checked before entering backend Working Memory. This frontend performs semantic translation; business Rule decisions and numeric reasoning happen downstream. A pre-authored Event Graph can also enter directly, but passes the same backend contract checks.

02 — Meaning and exact data coexist in a Span

core_vector, relation_vector, and nature_vector help access concepts, relations, and attributes. Exact fields such as span_id, feature_type, value, unit, entity, period, and evidence references support binding and calculation. For example, “beginning accounts receivable” can be described by accounts_receivable / temporal_role / beginning; semantic compatibility does not erase the exact value or its scope.

03 — Control, retrieval, and matching

The Scheduler invokes Control Rules to select a strategy or Rule selector. Retrieval proposes Knowledge definitions and candidate Rules. Matcher then binds required slots to current spans and checks declared relation, source, identity, numeric, and task constraints. A highly ranked but inadmissible candidate cannot execute.

04 — Execution and structured feedback

Executor applies supported produced operations, including graph updates, Rule selectors, and deterministic calculation through Calculator. New spans can satisfy later Rule requirements. Missing conditions, rejected bindings, and execution errors provide feedback that Control can use to revise a path, request supported Knowledge completion, or seek a scoped frontend clarification.

05 — Acceptance before presentation

Output requires an approved result for the current task, an unambiguous Event scope, valid target references, and consistent snapshots. Decoder builds an answer from retained structure and values. For unit-bearing numeric answers, a language model may improve the wording, while number and unit guards preserve a deterministic fallback if verification fails.

Released scope: This flow describes the public two-domain Demo v0.1. General recursive subgoal stacks, full dependency invalidation, Auto-Learn, and training are not included in that release. See the module architecture.

03 — Nomination vs. admission

Similarity proposes. Conditions decide.

Semantic retrieval answers which Rule might be relevant? Admission answers which binding is supported by the facts of this task? A candidate is first nominated using semantic and structural information; its required slots must then be grounded in the current Event state and satisfy the Rule's declared applicability contract.

$$r=\langle Req_r,\ Prod_r,\ C_r,\ \Phi_r\rangle \tag{6}$$
A low-level rule declares a required premise pattern, an expected effect, applicability conditions, and an execution operator.
$$Adm(r,b;S_t)=\mathbf{1}\!\left[Req_r(G_t,b)\ \wedge\ C_r(G_t,b,q)\right] \tag{7}$$
For binding b: the first conjunct requires grounded premises; the second checks object identity, units, time, exceptions, and the task's allowed evidence. Repeated occurrences of a variable must bind consistently.

In the released pipeline, retrieval and pre_match narrow the candidate scope. Matcher checks declared slot types, three-channel semantic compatibility, source requirements, relations, shared bindings, and the applicable numerical or temporal constraints. Scheduler may rank admissible candidates by goal, priority, or prior path preference, but cannot promote an unmatched candidate solely because of similarity.

Strictness is relative to the declared Rule contract. A structurally valid but incorrectly interpreted source can still lead to an incorrect conclusion, and Matcher cannot enforce an important domain condition omitted from the Rule. The implementation also permits controlled temporary revision of explicitly soft requirements; this is distinct from evidence-backed completion of a missing hard premise.

This is nomination–admission separation. Semantic access remains flexible about expressions and candidate meanings, while execution eligibility stays inspectable under current evidence. Representation models and domain Rules can evolve separately if their graph and matching interfaces remain compatible.

Example — similar financial terms, different eligibility. Suppose a DSO task requires net credit sales for FY2025, but an available figure belongs to FY2024 and another is merely labeled “revenue.” All may be semantically close to the denominator. Only a value satisfying the Rule's declared entity, period, measurement basis, and evidence conditions can be bound. Otherwise, the system must not silently substitute a nearby number.

04 — Composition

The hierarchy is built, not prescribed

ERS distinguishes two functional categories of Rules. Low-level execution Rules specify local transformations over current Event facts. High-level Control Rules organize goals, candidate continuations, and strategy revisions when premises are missing or operations fail. The two categories serve different responsibilities; they do not prescribe exactly two levels in every reasoning process.

In the theory, a Control Rule can invoke a more specialized Control Rule, producing multiple task-dependent levels of subgoals and local plans. Useful depth depends on the problem and available budget; greater depth also creates overhead. Control observes active goals, pending candidates, and execution feedback, so the next decision can change as the state changes.

$$Z_t=\langle\zeta_t,\ \preceq_t,\ \mathrm{Cand}_t,\ \mathrm{Bud}_t\rangle \tag{9b}$$
The active control state records the selected subgoal, dependency ordering, candidate organization, and remaining resources. A high-level rule specifies when an organizational transformation applies and what control state it produces.

Control directs execution; execution and state changes redirect Control. Theoretical Control may recursively reorganize subgoals. The public Demo implements bounded child_rule_selectors, strategy switching, Scheduler recovery, and Matcher/Executor feedback, while the Scheduler still manages fixed runtime stages and resource limits. A general nested subgoal call/return stack and research dynamic intermediate strategies are not released. Control depth, Rule execution count, and lookahead depth are different quantities.

Knowledge completes definitions; Memory guides exploration

Knowledge — supported semantic completion

Knowledge contains reusable conceptual definitions, not missing measurements for the present task. When a Rule requires a semantic property not yet established, the system can retrieve its definition and test the current spans against declared evidence conditions. Supported completion adds a new provenance-bearing semantic span and preserves the original value, unit, entity, and period, then triggers rematching. Available activation modes include explicit_components, single_core, all_cores, and relation_context. Unsupported or ambiguous completion is rejected.

Memory — previous paths as hints

Historical traces may prioritize a promising Rule continuation, but they cannot turn an old answer into a current fact. All bindings are reconstructed from present evidence, and every Rule still has to meet its applicability conditions. Demo v0.1 includes runtime Memory interfaces but does not distribute a learned historical-memory corpus, Rule reconstruction, or an Auto-Learn process.

Practical distinction: Knowledge may justify a concept under current evidence, but cannot invent an absent FY2025 sales figure. Memory may recommend trying an averaging Rule first, but cannot reuse yesterday's DSO value as today's measurement.

05 — Finite rules, open paths

The same library, paths it never stored

A Rule is a reusable local capability, not a memorized answer to an entire task. Its required side specifies input patterns and constraints; its produced side specifies an admitted graph transformation, calculation, selector, or Control operation. Slots are rebound to today's entities, values, periods, and evidence. An accepted output may satisfy another Rule's requirements, so a finite library can support paths never stored as complete recipes.

For example, an averaging Rule can derive a balance from valid beginning and ending measurements. A subsequent ratio Rule can then consume that derived value with the currently authorized denominator and period convention. The same local operations may serve different tasks when their input bindings and constraints are satisfied. The composition is formed during inference, not retrieved as a prewritten whole-solution template.

Three levels must be kept distinct: expressibility (whether a Rule composition exists), reachability (whether it can satisfy the goal using valid current facts), and discovery (whether Control can find and execute it within budget). Reusable Rules alone do not imply general-domain coverage, search optimality, or automatic induction of missing capabilities.

$$Accept_q(S_T,H_T)=\big[g_q(G_T)\ \wedge\ C_q(G_T,H_T)\ \wedge\ Evidence_q(G_T,H_T)\big] \tag{13}$$
Stopping an inference episode does not imply that the goal has been achieved: a conclusion is accepted only when the goal, the task constraints, and the actual evidential support are satisfied. Task success, path validity, and conformance to a particular reference mechanism are three separate quantities.

An inference episode ending, a plausible number, or a previously successful path does not establish an accepted solution. Goal satisfaction, task constraints, and present evidential support must jointly authorize the result.

06 — Revision

A withdrawn premise is not a disproof

In the paper's dependency-maintenance design, a derived conclusion may have multiple supporting justifications, and each justification may require several premises. Every premise of a given support must remain valid; a conclusion can survive if another independent support remains valid. Withdrawal of evidence removes its support without proving the opposite claim.

$$\mathcal I(S_0)\ \wedge\ \bigwedge_{t=0}^{L-1}\left[\mathcal I(S_t)\Rightarrow\mathcal I(S_{t+1})\right]\ \Rightarrow\ \mathcal I(S_L) \tag{15}$$
Proposition 2 (conditional path consistency). If declared state invariants hold initially and every accepted transition preserves them, they hold after any finite sequence of accepted transitions. This states how local checks compose across a long execution path; it does not by itself certify the factual truth of an input or the correctness of a misspecified domain rule.

Dependency-scoped revision is a research mechanism. The candidate scope for revalidation is the dependent closure, while conclusions with independent valid supports may remain accepted. This principle is examined in the paper's targeted fact-change scenarios; the public Demo does not yet include the complete general-purpose maintenance engine.

Three structures matter: Control organization records which goal and path are currently pursued; derivation dependencies identify which premises support each result; and execution history records attempts and failures in chronological order. An execution log alone cannot identify every affected downstream conclusion when a premise changes.

For example, revising an upstream revenue value may require rechecking a derived DSO result, while an independently calculated average receivables balance can remain valid if its own observations have not changed. If another valid support for a conclusion survives, that support must be considered before retracting the conclusion.

Theory / Demo boundary: The paper studies targeted premise-change scenarios and dependency-scoped revalidation. Demo v0.1 retains selected computation sources, alignment fingerprints, strategy histories, and output snapshot checks. It does not publish a general truth-maintenance ledger for arbitrary downstream invalidation, preservation of independent support, or automatic Rule rebinding after arbitrary edits.

07 — Search

Looking ahead before committing

Reusable Rules create a combinatorial decision problem: several candidates may match a state, and each valid intermediate result can open new continuations. If the system commits to every attractive branch, it may execute many operations that later prove irrelevant, blocked, or less useful for reaching the goal.

High-level Control uses the current goal, subgoal prerequisites, candidate organization, and failure feedback to restrict or reorder expansions. The paper's prospective lookahead studies bounded future continuations before committing to domain operations. This can reduce unnecessary executed steps while increasing candidate-evaluation work.

$$c_{control}<(B_t-K_t)\,c_{test} \tag{19}$$
Under a transparent cost model, hierarchical control is cheaper exactly when the avoided expansion cost exceeds the overhead of organizing the smaller candidate set. Whether hierarchy pays therefore depends on the relation between control overhead and avoided expansion cost — which the paper makes explicit rather than assuming.

The relevant objective is total resource cost: Control pays off when avoided search and execution exceed the cost of organizing and revising strategy. Fewer executed business Rules do not automatically imply less CPU time, wall-clock latency, or provider-token cost. The paper's lookahead measurements and dynamic-control comparisons are research results; the released Demo's bounded selectors and counters do not constitute the same matched-budget benchmark.

09 — Failure

Failure is an inspectable output

Useful failures preserve where a path stopped. The observable cases include malformed or misleading semantic input; a retrieved Rule whose required pattern cannot be met; a binding violating source, entity, or period constraints; an Executor or Calculator error; an ambiguous output reference; and a search attempt that reaches its budget without supported completion.

These observations lead to distinct interventions: Knowledge may prove a missing semantic definition and allow rematching; a scoped frontend request may clarify a source expression; Control may choose another admitted candidate; Executor errors may trigger strategy review; and an output failing its gate is withheld. The released runtime distinguishes solved, blocked, incomplete, unresolved, and runtime_failed. Completion of a runtime lifecycle is not by itself a solved task.

The paper is explicit about the limit: the cause of a symptom may require additional evidence. An erroneous semantic encoding can appear locally identical to a rule-condition mismatch unless the encoding is checked against an external source, and failure to retrieve a rule cannot be distinguished from the absence of a usable rule solely from an empty admitted set.

10 — Worked example

One task, end to end

Days Sales Outstanding (DSO) illustrates the difference between knowing a formula and executing a justified reasoning path. A plausible number is insufficient if the receivables belong to the wrong entity, the denominator uses an unauthorized sales basis, or reporting periods are incompatible. ERS treats the measurements as scoped Event facts, checks their eligibility against declared Rule requirements, derives intermediate values through admitted operations, and gates the result on the task goal and available evidence.

How the released inference pipeline executes this idea

The semantic frontend recognizes the DSO goal and candidate measurements; the graph boundary validates their structure. A Control Rule chooses the domain strategy. Matcher then binds current spans according to the Rule's declared entity, period, and measurement constraints. If an average receivables value must first be derived from beginning and ending balances, an admitted averaging Rule writes its result into the Event workspace. A later ratio Rule consumes that supported value together with the authorized denominator and day convention.

Calculator computes the numeric result, Executor records the producing operation and available source information, and Output Gate determines whether the current Event has an eligible approved target. Decoder constructs a grounded answer, with guarded wording for unit-bearing numeric values.

Independent numerical illustration: if average accounts receivable is 120, net credit sales is 960, and the authorized period is 360 days, then 120 / 960 × 360 = 45 days. The difficult part for a reasoning system is verifying the eligibility of those three inputs. An ordinary “sales” or “revenue” figure cannot automatically replace net credit sales. The paper's Figure A1 uses its own explicitly authorized assumptions and values; this numerical illustration is separate from that figure.

Implementation boundary: The public Demo shows structured binding, deterministic calculation, feedback, and output guarding. General automatic invalidation and rebinding of all downstream conclusions following arbitrary upstream edits remains a broader research mechanism.

11 — Roadmap

Where do we go from here?

The next step is to connect the paper's formal mechanisms, the released two-domain inference architecture, and independent end-to-end evidence under explicit budgets and well-defined failure categories.

Matched-budget comparison

Compare Control policies under explicit, matched candidate limits, lookahead depths, Rule-execution budgets, and recovery constraints. Include repeated runs, completion and abstention outcomes, input-to-output latency, backend CPU time, candidate checks, executed steps, and provider-token usage.

Independent topological holdout

Hold out independent Event and Rule graph topologies with frozen acceptance criteria. Distinguish new combinations of existing Rules from induction of new capabilities, and test both supported derivations and justified refusals under varied semantic inputs.

Cost of dependency-scoped revision

Implement general provenance and dependency maintenance and measure affected closure, surviving independent supports, correctness after changes, and cost against full recomputation. Evaluate historical-path Memory separately from learning or rewriting the Rule library.

Beyond Demo v0.1: Auto-Learn, Rule reconstruction, full recursive subgoal execution, and multimodal grounding remain distinct research and engineering directions.

Together these retain the central architectural question: how finite local capabilities, explicit evidence dependencies, and task-dependent control can support new solutions and maintain their validity as the problem changes.
